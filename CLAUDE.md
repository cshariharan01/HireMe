## What this is

HireSignal Personal Edition — a single-user, localhost job search tool focused on healthcare IT. Next.js 14 (App Router) + SQLite + local Ollama. No cloud services; everything runs on `localhost` against `http://localhost:11434` (Ollama) and `./data/hiresignal.db`.

## Prerequisites

Ollama must be running locally with both models pulled: `nomic-embed-text` (embeddings) and `llama3.2` (chat). The app will throw on the first API call if Ollama isn't reachable. Env overrides live in `.env.local` (see `.env.example`).

**Testing.** `npm test` runs **Vitest** (`vitest.config.mts`). `pool: 'forks'` is REQUIRED — the
default worker-thread pool cannot load the `better-sqlite3` / `sqlite-vec` native addons — and
`fileParallelism: false` because the DB suites share one fixture file. Suites that touch SQLite must
`import './setup-db'` FIRST: it sets `HIRESIGNAL_DB` to a temp file before `src/lib/db.ts` resolves
its path at module-evaluation time. The suite exists because a code review found two defects on the
primary user path that the 17-check browser E2E could not see (see `test/apply-documents.test.ts`
and `test/sync-prune-guard.test.ts`) — prefer a unit regression test for logic errors, and the
browser driver (`.notes/scripts/e2e-verify.ts`) for anything user-visible.

Scripts run via plain `npx ts-node scripts/<file>.ts` in **CommonJS** mode. This is required (Next's `tsconfig` is `module: esnext`, but ts-node needs CJS for `better-sqlite3`/`sqlite-vec` native modules AND for extensionless local imports to resolve at runtime). **The ts-node override lives in `tsconfig.json`'s `"ts-node"` key** (`{ "compilerOptions": { "module": "commonjs", "moduleResolution": "node" }, "transpileOnly": true }`) — ts-node reads config from tsconfig.json, **not** package.json (the old package.json `ts-node` key never actually applied; it worked only because the old scripts had no local relative imports). Because of this, scripts may now import pure `src/lib/*` modules (no DB side effects) and `scripts/shared/*` helpers directly. **Don't pass `--compiler-options '...'` inline** — the single-quoted JSON breaks Windows cmd.exe.

## Stack

Next.js **15** (App Router) + React **19**, TypeScript, Tailwind, SWR. Upgraded from Next 14.2 /
React 18 — three things broke and are worth knowing:
1. **Route `params` is now a `Promise`** and must be awaited. `npx @next/codemod@canary
   next-async-request-api ./src` handled all 18 dynamic route handlers.
2. **`experimental.serverComponentsExternalPackages` → `serverExternalPackages`** (see below). The
   old key is ignored without warning, which would let Next try to bundle the native addons.
3. **`tailwind.config.ts` could no longer use `require()`.** Next 15's build writes
   `"target": "ES2017"` into `tsconfig.json`, after which Tailwind loads the config through Node's
   ESM-from-CJS path where `require` is undefined — the dev server crashed with
   `ReferenceError: require is not defined` while compiling the first page and every route returned
   a connection reset. Use a static `import`.

## Architecture

**Data flow:**
1. Ingestion scripts pull postings from ATS APIs → `job_postings` (no embedding yet), deduped by `sha256(source+company+title+location)` via the `dedup_hash UNIQUE` column.
2. `npm run embed` batches rows with `embedding IS NULL`, calls Ollama `/api/embeddings`, writes Float32Array as BLOB.
3. `/api/resume` POST parses PDF → `parseResume` → embeds raw text → upserts the singleton row at `my_profile.id = 1`.
4. `/api/matches` GET runs **hybrid retrieval** (sqlite-vec `vec_distance_cosine` + BM25 over the `job_fts` FTS5 index, fused with Reciprocal Rank Fusion), scores each candidate with the bounded composite in `src/lib/relevance.ts`, collapses duplicates, caps per-company, and caches the ranked payload into `match_cache` (NOT `match_results` — that table was v1 and has been dropped). See **Scoring signals** below.
5. `/api/generate/cover-letter` and `/api/generate/resume-variant` produce text from the stored `parsed_json`; prompts explicitly forbid inventing skills.

**LLM provider dispatch** (`src/lib/llm.ts`): the provider is resolved **DB-first with env fallback**, re-checked on every call behind a 30s cache (`getProvider()`). Resolution order: (1) the `llm_providers` row with `is_active = 1` — configured via the `/settings` UI and `/api/providers/*` routes; (2) env fallback preserving prior behavior — `GEMINI_API_KEY` (Gemini 2.5 Flash) → `ANTHROPIC_API_KEY` (Claude Haiku) → Ollama local. Supported `kind`s: `gemini | openai | anthropic | openai-compatible | ollama | freeway` — enforced by `llm_providers.kind`'s CHECK constraint, whose allowed list lives in `PROVIDER_KINDS` in `db.ts`. SQLite cannot ALTER a CHECK, so adding a kind means rebuilding the table: `migrateProviderKinds()` does exactly that (create-copy-drop-rename in a transaction, guarded by sniffing the stored DDL so it runs once and is a no-op on a fresh DB). Keep `PROVIDER_KINDS`, `ProviderKind`, `VALID_KINDS` (providers route) and the settings page's `KIND_OPTIONS` in sync. There's a separate **"creative lane"** (cover-letter + resume-variant generation) that prefers a provider flagged `is_creative = 1`, else Gemini 2.5 **Pro**→Flash — reasoning quality matters more there than throughput. Providers DO rotate on failure (`buildProviderChain`/`callWithProviders`): active DB row → other configured rows → **Freeway** → Ollama last, with a 429 putting the offending row on `cooldown_until` (6h for daily quota, 90s for a per-minute limit). Embeddings (`src/lib/embeddings.ts`) **always** go to Ollama regardless of chat provider. Gemini/Anthropic branches use native structured-output (`responseSchema` / `output_config`) for `parseResume`; Ollama falls back to regex-extract-JSON. `src/lib/llm.ts` also hosts `evaluateJob` and `researchCompany` (see AI scoring below).

**LLM timeouts** (`src/lib/llm.ts`): there were NONE — the raw fetches carried no `AbortSignal` and the Gemini/Anthropic SDKs default to no timeout, so a single hung provider pinned the awaiting API route forever (one `/api/jobs/[id]/format` call wedged the dev server at ~940MB and every route 500'd until it was killed). Every provider attempt is now bounded by `withLlmTimeout()` inside `callWithProviders` — deliberately at THAT layer, so a timeout is an ordinary provider failure and the chain **rotates** instead of failing the request. `LLM_CALL_TIMEOUT_MS` (default 120s) also drives `AbortSignal.timeout` on the two raw fetches, and the creative lane + grounded-search call are bounded too (they bypass `callWithProviders`).

**Freeway gateway — a first-class provider, and the fallback that isn't Ollama** (`src/lib/freeway.ts`, `scripts/test-freeway.ts`, `scripts/shared/env.ts`): cloud free tiers have hard daily quotas, and when they exhausted the chain used to drop to local `llama3.2` — too weak for ratings, resume tailoring and briefs. **Freeway** (the user's own OSS project, `D:/AI Projects/FreeClaude/freeway`) is a local gateway fronting ~32 free-tier providers with its own quota-aware routing, mid-answer failover and multi-key rotation. It slots into the chain **between the user's own keys and Ollama**, so an exhausted key degrades to another *capable* model. **Configured in `/settings` like any other provider** (kind `freeway`, own badge, Quick preset): Add provider → Activate to make it primary, or leave it inactive and it still serves as the fallback ahead of Ollama. Its **api_key field is optional** — a row with no key inherits `FREEWAY_API_KEY` at call time (`askOnce`: `options.apiKey || freewayApiKey()`), so the key can live in the DB or in `.env.local`. `base_url` is the gateway ROOT; `normalizeFreewayBase` strips a trailing `/v1` or `/api/v1/ask` so any form of the URL works. Env-only config still works with no DB row at all (`freewayEnvConfig`), and `chainTail`'s `pointsAtFreeway` + kind check stops it being queued twice when both exist — the DB row wins. Default base `http://localhost:8092` (Freeway's own stock default is 8082; this machine runs 8092).
- **Endpoint choice:** we call `POST /api/v1/ask` (plain JSON in/out, reports `model_used` + `was_fallback`, both logged). NOT `/v1/messages` (always streams regardless of the request) or `/v1/responses` (refuses non-streaming) — those serve Claude Code / Codex.
- **Freeway does NOT forward structured-output directives.** `response_format` is never read and its canonical request marks `output_config`/`extra_body` "accepted but never forwarded" — so Gemini `responseSchema` / Anthropic `output_config` do not survive the proxy. `runStructured`'s `freeway` branch therefore coaches the schema into the prompt and lets the caller regex-extract, exactly like the Ollama branch. Verified end-to-end: a real `evaluateJob` served by Freeway returned every schema key.
- **Freeway has no `/v1/embeddings`** (embedding models are filtered out of its routable catalog), so embeddings stay on Ollama `nomic-embed-text` regardless.
- **Reasoning-model budgets — two separate floors.** `MIN_MAX_TOKENS = 512`: the default model bills its thinking against the same budget, and `max_tokens: 80` returned reasoning instead of an answer (same reason the `/api/providers/[id]/test` ping went 32 → 256, and why the `freeway` test branch uses 512). **Timeout scales with the budget** (`timeoutFor`: 60ms/token, floor 120s, override `timeoutMs` or `FREEWAY_TIMEOUT_MS`) — a flat 120s cap was measured tripping on a real 4096-token evaluation, which then fell through to Gemini. Observed evaluation times: 21s / 34s / 50s / >120s.
- **One retry on 502 only** (Freeway has already exhausted its internal failover); 400/401/503 never retry. The free tier behind the gateway is ~50 req/day and 20/min, so don't loop it.
- `FreewayError`'s constructor calls `Object.setPrototypeOf` — kept deliberately. `tsconfig.json` now sets `"target": "ES2017"` (Next 15's build wrote it in), so this is belt-and-braces; it USED to be essential, because with no target tsc defaults to ES5 where subclassing `Error` breaks `instanceof` and ts-node scripts silently took the "not retryable" branch. Don't remove it — a future target change would quietly reintroduce that.
- **`scripts/shared/env.ts`** loads `.env.local` via `@next/env` for ts-node scripts, which previously saw NO `.env.local` values at all (only the app did). Imported first by `evaluate-top.ts` and `test-freeway.ts`; import it in any new script that reads env.

**In-app Sync** (`src/lib/sync.ts`, `scripts/run-sync.ts`, `src/app/api/sync/route.ts`, `src/components/sync-button.tsx`, `sync_runs` table): runs the pipeline from the UI. **DB-backed + detached** — this is deliberate and load-bearing: `startSync(mode)` inserts a `sync_runs` row and spawns **`scripts/run-sync.ts` as a DETACHED process** (`spawn(..., {detached:true, stdio:'ignore'}).unref()`) that runs the step scripts (quick = embed→prune→verify:links→evaluate:top; full = +ingest:all→discover first) and **writes live progress into the row** (`current_step`, `step_index`, `steps_json`, `log_tail`, `updated_at` heartbeat). `getSyncStatus()` reads that row — **no in-memory state**. Why: `next dev` recompiles routes on-demand, which re-evaluates server modules and would wipe any in-memory singleton (and it did — earlier versions died whenever the app was browsed mid-sync). DB-backed + separate process survives recompiles/restarts. `getSyncStatus` treats a `running` row with a stale `updated_at` (>120s) as dead. **Cancel** sets `cancel_requested` (the orchestrator polls it) AND does a Windows command-line-match kill via PowerShell (`Stop-Process` on any `run-sync.ts`/pipeline proc) — plain `taskkill /T` misses deeply-nested shell grandchildren. The `SyncButton` (sidebar) polls `/api/sync` and shows a **step checklist + live log line + elapsed timer + job counter + a fixed top indeterminate bar** (`.animate-indeterminate` in globals.css) so it's obviously alive even during the long ingest step. Note: `embed-jobs.ts` now embeds up to `EMBED_LIMIT` (5000, was 500) with no per-job delay.

**App shell + Notion-warm redesign** (`src/components/app-shell.tsx`, `src/app/layout.tsx`, `src/app/globals.css`, `tailwind.config.ts`): the top `Nav` is replaced by a left **sidebar** (`AppShell`: nav + `SyncButton` + theme/⌘K footer; responsive drawer on mobile). Design tokens shifted from cool zinc (hue 240) to **warm stone (hue ~30-40)** with soft shadows (`--shadow-soft`/`--shadow-pop`, `.shadow-soft`/`.shadow-pop` utils), a bigger radius (0.875rem), and a calm blue `--ring`. Because it's token-level, all pages inherit the warmth. `Card` is `rounded-xl shadow-soft`. Shared, de-duplicated helpers: `src/lib/score.ts` (`scoreTier`/`pctClamp`/`companyInitials`/tier classes), `src/components/ui/score-badge.tsx`, `src/components/ui/stat-tile.tsx`.

**First paint ships data, not a skeleton** (`src/app/page.tsx`, `src/app/dashboard-client.tsx`,
`src/lib/matches-page.ts`, `src/lib/match-keys.ts`): the dashboard route is now a SERVER component
that computes the default first page and seeds SWR with it via `<SWRConfig fallback>`, so the rows
are in the HTML instead of arriving one round-trip after hydration. Three things are load-bearing:
1. **The key must match `useMatches`'s `firstPageKey` character-for-character.** A seed under any
   other key is silently ignored — SWR just fetches, with no error. `matchesFallbackKey()` lives in
   `match-keys.ts`, imported by both sides. It CANNOT live in `hooks.ts`: that is a client module,
   and calling it from the server throws *"Attempted to call matchesFallbackKey() from the server"*
   — which a `try/catch` around the seeding hid completely, so the only symptom was the
   optimisation quietly doing nothing. That catch now logs.
2. **`export const dynamic = 'force-dynamic'`.** Without it Next prerenders the page as STATIC
   (`○ /` in the build output) and freezes whatever matches existed at build time.
3. **The route and the server render share `buildMatchesPage`** (`matches-page.ts`), so the seeded
   payload cannot drift from what `/api/matches` returns — otherwise first paint and post-hydration
   would render different shapes.
Measured in production: rows present in the server HTML with JS disabled (was 0), first row visible
970ms.

**The match list is NOT virtualized, deliberately.** Measured first: at 210 loaded rows the list is
~4,500 DOM nodes and typing latency is FLAT with row count (production: 161ms for 9 characters at 30
rows, 168ms at 210). `React.memo` on `MatchRow` plus stable `useCallback` handlers had already
removed the re-render cost, so a virtualized list would add real risk for no measured gain — and it
would break `j`/`k` keyboard nav and the detail route's prev/next, which resolve rows via
`document.getElementById('match-row-<id>')` and `scrollIntoView`. Instead the rows carry
`content-visibility: auto` + `contain-intrinsic-size` (`.match-row` in globals.css): the browser
skips layout/paint for offscreen rows while KEEPING them in the DOM.

**Dashboard counts come from `/api/stats`, not from the rows.** The stat tiles used to fetch the
whole digest and every application row (each carrying its stored cover letter and résumé variant)
purely to call `.length`. `useDashboardStats` reads two SQL COUNTs instead.

**Two-pane Matches** (`src/app/page.tsx`, `src/components/job-detail-panel.tsx`): the dashboard is now master-detail — a compact scored job **list** (left, own scroll) + the **detail pane** (right). The job-detail body was extracted from the route into `<JobDetailPanel jobId variant>` (`variant='pane'` hides the back/prev-next bar; `'page'` shows it); **`src/app/job/[id]/page.tsx` is now a thin wrapper** rendering it full-width. Selecting a row sets `?job=<id>` (shallow, deep-linkable) and auto-selects the top match on desktop; below `lg` a row tap navigates to `/job/[id]`. Keyboard nav (`j/k/e/x/`), hide/restore, filters, sort, saved searches, and bulk-evaluate are all preserved. NOTE: `JobDetailPanel` must live in `src/components/` (not exported from the route) — Next forbids extra named exports from a `page.tsx`. `page.tsx`'s default export wraps `<Dashboard>` in `<Suspense>` (required because it uses `useSearchParams`).

**Resume source for auto-apply — original vs AI-tailored** (`src/lib/apply/prepare.ts`, `apply/questions.ts` config, `apply/route.ts`, `auto-apply-dialog.tsx`): the upload now stores the **original PDF bytes** (`resumes.pdf_blob`/`pdf_filename`, mirrored to `my_profile`). `prepareSubmission(jobId, { resumeSource })` attaches either the user's original PDF (`resumeSource='original'` — no LLM, no render) or the AI-tailored variant (`'tailored'`). Default is `'original'` (apply_settings `resumeSource`); the auto-apply dialog has an Original/AI-tailored toggle (re-fetches the preview via `?resume=`). **`src/app/api/jobs/[id]/resume.pdf/route.ts` serves the preview** — POST `{source:'original'}'` short-circuits to the stored blob (no LLM/render), `{source:'tailored'}` renders the generated variant, `{markdown}` wins for the detail panel's download — and is covered by `test/resume-pdf.test.ts`. Note: the route file was at one point extracted into `render-pdf.ts` and the ROUTE ITSELF deleted (the file is in the `resumes` → `my_profile` pipeline; recreating the route fixed a UI 404 "PDF render failed"). If the active resume predates byte-storage, `resumeSourceAvailable.original=false` → falls back to tailored with a "re-upload to enable" warning. The generated-resume PDF template (`markdown-to-html.ts` `wrapInAtsTemplate`) was restyled more professionally (slate section accents, refined type) but stays ATS-safe.

**Multi-resume library** (`resumes` table in `src/lib/db.ts`, `src/lib/resumes.ts`, `src/app/api/resume/route.ts`, `src/app/api/resumes/**`, `src/app/profile/page.tsx`): the user keeps several resumes (e.g. generic + healthcare) and switches which is active. Design keeps `my_profile` (id=1) as the **live "active profile"** that every consumer (matcher, evaluate, generate, apply, digest) reads unchanged — `resumes` is the library, and the active row is **mirrored** into `my_profile` (`mirrorResumeToProfile`/`setActiveResume`). Upload (`POST /api/resume`, optional `label` form field) inserts a resume row + activates it; `GET /api/resumes` lists metadata; `POST /api/resumes/[id]/activate` switches (recomputes matches); `DELETE /api/resumes/[id]` removes (reassigns active to the most-recent remaining, or clears `my_profile` if none). `PATCH /api/resume` writes both `my_profile` and the active resume row. A one-time seed migration in `db.ts` imports any pre-existing singleton `my_profile` into `resumes` as the first active entry.

**Ollama robustness** (`src/lib/embeddings.ts`): `generateEmbedding` now (1) caps input to `EMBED_MAX_CHARS` (6000) — nomic-embed-text has a 2048-token context and a full resume/JD overflowed it (`"input length exceeds the context length"`, HTTP 500); (2) retries transient 5xx/network/timeout failures with backoff; (3) has a 30s AbortController timeout. **Default `OLLAMA_BASE_URL` is `http://127.0.0.1:11434` (IPv4), NOT `localhost`** — on Windows `localhost`→IPv6 `::1` is flaky against Ollama and was the root cause of intermittent résumé-upload failures. Changed everywhere (embeddings, llm, embed-jobs, settings presets, provider test). The resume route maps Ollama failures to a clear 503 message.

**Adaptive role targeting** (`deriveTargetRoles` in `src/lib/llm.ts`, `src/app/api/resume/route.ts`, `src/app/api/profile/roles/route.ts`, `src/app/profile/page.tsx`): on resume upload, the LLM derives 8-15 resume-fit role titles (healthcare-first but broad) stored as `parsed_json.suggested_roles`; `targets.roles` defaults to all of them. The profile page shows them as toggle chips (all-on, deselectable, "Regenerate"). Selected roles feed **hunting** — the keyword scrapers (`ingest-linkedin/hirist/naukri`) and career-page discovery read them via `scripts/shared/profile-roles.ts` (`resolveRoleQueries`), falling back to their hardcoded defaults — and **ranking** — the matcher adds `roleTargetBoost` (+0.04) when a job title matches an enabled role (soft, never a hard filter).

**Freshness & validity engine** (`src/lib/link-check.ts`, `scripts/prune-stale.ts`, `scripts/verify-links.ts`, `scripts/shared/freshness.ts`, matcher): ingestion is no longer append-only. Every `scripts/ingest-*.ts` (except `layoffs`, which uses a different table) now **upserts** — `INSERT ... ON CONFLICT(dedup_hash) DO UPDATE SET last_seen_at=CURRENT_TIMESTAMP, source_present=1, posted_at=COALESCE(...)` — and calls `markSourceAbsent(db, source)` before its run + `ensureFreshnessColumns(db)` after schema setup (hirist also `touchStmt`s already-seen rows it skips re-fetching). New `job_postings` columns: `last_seen_at`, `posted_at`, `source_present`, `url_status`, `url_checked_at`, `expired_at`. `prune-stale.ts` retires jobs by **last_seen_at age** (not `source_present` alone — a failed/blocked source run would wrongly wipe a whole source), by **posting age** (`MAX_POST_AGE_DAYS`, default 180 — REQUIRED because last_seen_at alone can never retire a re-listed archive: HN's threads are permanent, so 390 rows from 2015-2020 stayed live forever), plus `url_status='dead'`, and resurrects re-seen ones. It has a **mass-expiry guard**: if the age rules would retire more than `MAX_EXPIRY_RATIO` (40%) of the active corpus it refuses and exits 2, because that means ingest did not run — the QUICK sync mode (`embed`→`prune`→`verify:links`, no ingest) would otherwise expire everything and leave 0 matches. Override with `PRUNE_FORCE=1`. `PRUNE_PURGE_DAYS=N` opts into permanently DELETING long-expired rows, but **orphans only** — four tables carry a FK to `job_postings` with ON DELETE NO ACTION, so a blanket delete fails outright, and applications/evaluations must never be destroyed. Test any prune change against a copy first: `HIRESIGNAL_DB=/path/copy.db npx ts-node scripts/prune-stale.ts`. `ingest-hn.ts` uses Algolia's **`search_by_date` with `numericFilters=created_at_i>`** — the old `/search` endpoint ranks by RELEVANCE, so it deterministically pulled the most *popular* "Who is hiring" threads of all time (2015-2017), and the title filter is anchored (`/^ask hn:\s*who is hiring\?/i`) so meta-discussion threads aren't scraped as jobs. `verify-links.ts` HTTP-checks the top `MATCH_LIMIT×2` matches via `checkJobUrl` (ATS-precise for Greenhouse/Lever, generic otherwise) and expires dead links. The matcher excludes `expired_at IS NOT NULL` / `url_status='dead'` by default (override `include_expired=1`) and adds `freshnessScore` (+0.05 ≤7d … −0.10 >90d) keyed off `posted_at`/`last_seen_at`.

**Career-page discovery** (`src/lib/discovery/{ats-detect,ats-pull,crawl}.ts`, `scripts/ingest-companies.ts`, `scripts/data/companies.txt`, `src/app/api/jobs/discover/route.ts`, import page): given a company **name or careers URL**, `detectAts` finds the ATS and `pullBoard` normalizes the whole board; `crawlCareersPage` (Playwright, JSON-LD `JobPosting` then heuristic link scrape) is the fallback. Discovered jobs use `source='company'`.

**Company directory** (`ats_companies` table, `scripts/sync-company-directory.ts`, `/api/companies/directory`, `src/components/company-finder.tsx`): a searchable index of ~37,000 company career boards — which ATS a company uses and its board URL — populated by `npm run sync:directory` from the free MIT dataset at `storage.stapply.ai/jobhive/v1/companies.csv` (~80k companies, 7MB; only rows on ATS platforms we can actually pull are stored). It is a DIRECTORY, never a job source: postings are still pulled fresh by our own adapters, so only the company→ATS mapping is third-party, and that changes slowly. This exists because seeding a Workday employer was otherwise near-impossible — tenant + data-centre + site cannot be derived from a name (15 probes across Kaiser/HCA/Providence/Cigna/Elevance found zero boards); here they arrive pre-resolved. **Search ranking is load-bearing**: a plain `LIKE '%q%'` surfaced "Relevance AI" for "Elevance" and "Mayors Migration Council" for "Mayo", so results are tiered exact → prefix → word-start → substring and a `partial` hit is badged "loose match". The JOBS slices of that dataset are deliberately NOT ingested — 7.8GB as CSV (Workday alone 4.3GB) versus 7MB for the directory.

**14 ATS platforms are supported**: Greenhouse, Lever, Ashby, SmartRecruiters, Recruitee, Workday, Workable, Breezy, Pinpoint, BambooHR, Personio, Teamtailor, Rippling, Manatal. Each was verified end-to-end against a real live tenant — `.notes/scripts/verify-all-adapters.ts` drives `detectAts → pullBoard` per platform and asserts a non-zero job count (14/14). **Never add an adapter without that proof**: a half-wired one is worse than none, because detection "succeeds", the pull returns nothing, and the crawl fallback is suppressed — exactly what `case 'workday': return []` did.

**Probes MUST require a non-empty board.** Three false positives came from accepting an HTTP 200: SmartRecruiters answers `{"totalFound":0,"content":[]}` for *any* slug (so every company looked like SmartRecruiters, and the crawl never ran); an Ashby board literally named `jobs` exists and is empty; and `jobs.recruitee.com` is a real board owned by someone else, so deriving a slug from a hostname would import ITS jobs under the wrong company. `GENERIC_HOST_PREFIXES` (jobs, careers, api, ats, board, platform…) are never probed for that last reason. Helpers: `nonEmptyArray` / `nonEmptyTopLevelArray`.

**Workday is URL-only, deliberately.** A pull needs tenant + data-centre host + site, and none can be guessed from a company name (15 probes across Kaiser/HCA/Providence/Cigna/Elevance returned zero boards). `parseWorkdaySlug` extracts the three from a board URL, and `detectAts`'s HTML sniff often finds that URL on the company's ordinary careers page — verified for Cigna (40 jobs) and Elevance (326).

**XML/RSS feeds (Personio, Teamtailor) are parsed with regex helpers**, not a dependency: `xmlBlocks` / `xmlTag` / `textOf` in `ats-pull.ts`. Note their `new RegExp(\`…[\s\S]…\`)` double-escaping — inside a TEMPLATE LITERAL `\s` collapses to a literal `s`, which silently turned the class into `[sS]` and made every XML feed parse to zero jobs. The `/import` page's "Discover from career page" tab posts to `/api/jobs/discover` (leaves `embedding` NULL → run `npm run embed`).

**Breadth gate** (`src/lib/seniority.ts`): `isSeniorRelevant(title)` keeps senior/technical/architect roles across any industry and drops junior/sales/non-eng noise. Applied as `isDomainPriority(...) || isSeniorRelevant(title)` in the broad sources (`himalayas`, `wwr`, `4dayweek`) and discovery — healthcare-IT always passes, non-healthcare senior roles still surface. This is the "explore all jobs, healthcare-first" behavior; `domain_priority` remains a ranking boost, never a filter.

**Server-side top-N evaluation** (`scripts/evaluate-top.ts`): evaluates the top `MATCH_LIMIT` active, embedded, unevaluated matches via `evaluateJob`, so ratings are complete without the UI's manual "Evaluate top 30". Uses the canonical `src/lib/db` handle (not a second one).

**Job classification + soft-rank** (`src/lib/job-classifier.ts`, ingestion scripts, `src/app/api/matches/route.ts`): Every ingested job gets tagged with `remote_policy` (`global` | `us-only` | `country-specific` | `unknown`), `visa_sponsorship` (bool), `relocation_offered` (bool) via regex keyword scan at insert time. The matcher no longer hard-filters by location — it applies a soft score (`+0.05` India/remote-global, `+0.03` visa/relocation, `0` vague-remote, `-0.10` US-city, `-0.20` explicit US-only) so everything stays visible with context badges on dashboard cards. Classifier regexes are duplicated across `scripts/ingest-{greenhouse,lever,ashby}.ts` to match the existing inline-duplication pattern; `src/lib/job-classifier.ts` is the canonical version that Next.js code imports. Keep them in sync when editing.

**Scoring signals — hybrid retrieval + bounded composite** (`src/lib/matches.ts`, `src/lib/relevance.ts`, `src/lib/skills-vocab.ts`, `src/lib/score.ts`):

The old model was `finalScore = cosineScore + ontologyBoost + rolePenalty + locationScore + evalBoost + legitimacyPenalty + roleTargetBoost + freshnessScore`, rendered as `round(finalScore * 100)`. It was replaced because it was **not a fit score**: `nomic-embed-text` cosine only spans ~0.29-0.83 over this corpus, so everything plausible read 70-99%; the sum **exceeded 1.0** and was clamped, making seven unrelated jobs all display "100%"; and nothing compared the candidate's skills to the JD's (a `Java Solution Architect` scored 98% for a candidate with no Java).

- **Retrieval is hybrid.** Two legs — `vec_distance_cosine` (semantic) and **BM25 over an FTS5 index** (`job_fts`, external-content over `job_postings`, set up in `db.ts:setupJobFts`) — fused with **Reciprocal Rank Fusion** (`1/(60+rank)` per leg). RRF compares *ranks*, never raw scores, because a 0.78 cosine and a −25.7 BM25 are on unrelated scales. The lexical query is built from the profile's own vocabulary (target roles + résumé skills + `domain_terms`). Degrades to vector-only if FTS5 is unavailable.
  - **The FTS query shape is load-bearing:** MATCH + ORDER BY + LIMIT must happen in a **subquery**, and only then join `job_postings` to filter. Joining first measured **5,629ms vs 33ms**. Do not "simplify" it.
  - `SELECT COUNT(*) FROM job_fts` reads the CONTENT table, not the index — it returns the full row count even when the index is empty. Detect an unbuilt index with a MATCH probe (see `setupJobFts`), and populate with `INSERT INTO job_fts(job_fts) VALUES('rebuild')`.
- **The score is a bounded weighted composite** (`scoreComposite` in `relevance.ts`), 0-100: retrieval 40% · **skill overlap 25%** · LLM `overall_score` 25% · context (location/freshness/legitimacy) 10%. Unevaluated jobs redistribute the LLM weight (retrieval 55% / skills 35%), otherwise every unrated job would be structurally capped at 75. `retrieval` is normalised against the **best observed** RRF, not the theoretical max — normalising against "rank 1 in both legs" measured a corpus topping out at 78 with nothing in the high tier.
- **Skill fit is the signal that did not exist.** `analyzeSkillFit` compares JD requirements against résumé skills using `skills-vocab.ts` — a canonical vocabulary with **word-boundary matching**, so `Java` does not match `JavaScript`. Title requirements count double. Single-letter skills (`C`, `R`) are deliberately excluded: `c` matches the "C" in "C-CDA".
- **Hard constraints, not soft boosts.** `targets.must_haves`, `targets.deal_breakers`, `targets.comp_min` and `targets.locations` are now READ at ranking time (they were written by `/profile` and ignored). A deal-breaker caps the score at 15; AI "skip" caps at 45; a missing title-skill or must-have subtracts.
- **`reasons[]`** — the "why matched" chips rendered on each row (`buildReasons`), negatives first, because the complaint was that a bad match looked good. They replace the old locationBadge / "In focus" / eval badges on the row.
- **`finalScore` is now exactly `score / 100`**, kept so `pctClamp(finalScore)` consumers (ScoreBadge, detail panel) render the new number unchanged. `ScoreBadge` no longer appends "%".
- **Duplicate collapsing + per-company cap** (`diversify()`): 793 duplicate company+title groups = 1,341 redundant rows (19%) existed because `dedup_hash` includes `location`. Collapsed at READ time (changing `dedup_hash` would orphan history) into `variants[]`, shown as a "N locations" chip; max 3 rows per company, overflow appended rather than dropped.
- **Applied jobs are excluded by default** (`includeApplied` opts back in), so the list backfills — and all three rating paths skip them (`evaluate-top.ts`, `/api/jobs/[id]/evaluate` returns 409 unless `?force=1`, and `bulkEvaluate` inherits the exclusion). They live in `/tracker`, which is already a full Kanban; the dashboard links to it rather than duplicating it.
- **Filtering and facet counts are SERVER-side** (`/api/matches`). They used to run in the browser over ~30 loaded rows out of a 500-row pool out of ~7,000 jobs (a 0.42% window), which is why chips like "Visa"/"US city" rendered disabled at 0. `POOL` was raised 500 → **1200** because the filters run over it, and **POOL is part of the cache signature** (raising it otherwise has no effect until the cache busts). Facets are counted per-filter with the *other* filters applied, so cross-filtering reads correctly.
- **`rolePenalty` is now actually applied.** It was computed in `matches.ts`, stored on the row, and never passed to `scoreComposite` — so non-technical postings silently stopped being down-ranked when the composite replaced the additive model. It now feeds `contextScore` at the same ×2 scale as the other additive terms.
- **Tier thresholds are calibrated to the real distribution** (`TIER_HIGH/GOOD/FAIR = 55/45/33` in `src/lib/score.ts`). The inherited 80/65/50 put 95.1% of the corpus in "low" — every filtered view rendered as a wall of grey. Re-derive them whenever the scoring model changes.
- **`evaluate-top.ts` ranks with this engine**, not `ORDER BY vec_distance_cosine`. It used to spend LLM quota on a completely different set of jobs from the ones the dashboard shows. Embedding similarity remains as a cold-cache fallback.
- **The parsed payload is memoised** (`matchMemo` in `matches.ts`, keyed by `cacheKey + signature + computed_at`, hung off `globalThis` like `db`). The ~1.6MB payload was re-read from SQLite and re-parsed on every request, including `/api/matches/[jobId]` which wants ONE row — use `getRankedMatchById()` for that, it's a Map hit. A memo hit reads only two small columns and never touches the blob.
- `SCORING_VERSION` is in the cache signature — bump it whenever the scoring model changes, or stale payloads keep serving old scores. Currently `score-v3`.

**AI job scoring vs. company research — two distinct LLM flows** (both cached, both provider-agnostic):
- **Per-job evaluation** (`evaluateJob` → `job_evaluations`, keyed by `job_id`; route `POST /api/jobs/[id]/evaluate`, `?refresh=1` forces recompute). Scores a single posting against the profile across CV-alignment / north-star-fit / compensation / culture / strategy + an `overall_score` and `recommendation`.
- **Per-company brief** (`researchCompany` → `company_briefs`, keyed by normalized `company_slug`; route `/api/companies/[slug]/research`). A recession-resilience-first lens (financial health, funding, layoffs, culture, legitimacy) reused across *all* roles at that company.

**Company intelligence sources** — lazy, on-view, per-company caches that feed both the briefs and the UI panels. Each has its own table and route under `/api/companies/[slug]/*`:
- `src/lib/levels.ts` → `compensation_data` (Levels.fyi; Playwright to read hydrated `__NEXT_DATA__`; regions US=254 / IN=43; `?refresh=1` to refetch).
- `src/lib/ambitionbox.ts` → `ambitionbox_data` (India ratings/salaries/reviews; **plain fetch + cheerio** — Ambitionbox blocks Playwright with HTTP/2 errors, so don't switch it to a browser).
- `src/lib/layoffs.ts` → `layoffs_data` (pure SQL lookup; data is **bulk-ingested** via `npm run ingest:layoffs`, not scraped on view).

**Auto-apply subsystem** (`src/lib/apply/*`, `/api/jobs/[id]/apply`, `/api/apply/config`): `prepare.ts` orchestrates a `SubmissionPlan` — load job+profile, `router.ts` picks a strategy from the URL (`greenhouse | ashby | linkedin | naukri | browser | manual`), generate/load cover letter + resume variant, render a resume PDF (`render-pdf.ts`, Playwright), then per-portal fetch the form schema and answer each question. **NO portal is submitted to directly.** Greenhouse direct submit is DISABLED (`GREENHOUSE_DIRECT_SUBMIT_AVAILABLE = false`): `boards-api.greenhouse.io` answers every POST with `401 HTTP Basic: Access denied` + `WWW-Authenticate: Basic realm="Application"`, and a POST to a NONEXISTENT board returns the same 401 — the gate is on the endpoint, before any board lookup, and the credential is an employer-issued key. GET is public, which is why plan-building and dry-run always looked healthy while submission was structurally impossible (this is why `apply_audit` had 0 successes all-time). **Ashby direct submit is likewise DISABLED** (`ASHBY_DIRECT_SUBMIT_AVAILABLE = false` in `router.ts`) because Ashby stopped inlining the form schema in the page and now gates submission behind reCAPTCHA — verified across 6 distinct company boards, so Ashby URLs route to `browser`. **LinkedIn** (`linkedin.ts`) and **Naukri** (`naukri.ts`) are dedicated adapters — visible, persistent-context Playwright that opens the real platform form, fills standard fields from the profile, answers prepared chatbot/step questions, attaches the tailored resume, and **STOPS when it detects the final Submit button** (the user reviews and submits manually; the browser window stays open). Locale/`--lang`/`Accept-Language` headers alone CANNOT stop the recurring "job in Arabic" symptom: LinkedIn decides the language server-side and reads it OFF the `lang` cookie. The cookie format is NOT `en_US` (verified live: `lang=en_US` and `?lang=en_US` do nothing) — the on-page language switcher writes `lang="v=2&lang=en-us"`, and setting that (on BOTH `.linkedin.com` and `.www.linkedin.com`) + reload flips a rendered `html lang="ar"` page back to English. `seedLinkedInEnglish` writes it BEFORE navigation so the first request is already English; `forceLinkedInEnglish` re-asserts + reloads after load. When a LinkedIn job has NO Easy Apply but carries an offsite "Apply" link (`detectLinkedInExternalApply` matches `a.jobs-apply-button`/`aria-label` "Apply on company website"/offsite tracking anchors — never the Easy Apply `<button>`), `linkedInApply` navigates the SAME window (a second context cannot share the profile dir) to the external URL, and runs `revealApplyForm` — clicks the site's own apply opener to expose the form (career sites show a description first), follows new-tab popups, and only treats a page as fillable when it has real application fields (`hasFillableApplicationForm`: file/email/tel/textarea/first/last/name/phone) so a board's search box or a cookie banner never produces a fake success. It then runs the generic `autofillPage` heuristics extracted from `browser.ts` (`browserAutofill` and the adapter handoff both call it) and still returns `stopped_for_review`. Non-fillable outcomes stay honest and are classified, in order: **a login/sign-in page** (visible password field or authN URL — Accenture-style portals redirect to one after Apply) or **a CAPTCHA gate** (Turnstile/reCAPTCHA) triggers a **Windows popup notification** (fire-and-forget `WScript.Shell` `Popup` so the user is told even when working in another window) and a wait of up to 10 minutes that **continues filling automatically** once the user signs in / solves the challenge and the employer form renders — the profile session is then reused on next apply; Greenhouse's `?error=true` dead-link marker (or `"no longer available"`/closed body copy) is reported as a closed posting; and anything else returns a clear error. **The window is left open for manual completion in every non-fillable case, and no CAPTCHA is ever solved programmatically.** DOM knowledge adapted from `Harshitsk7/jobpilot` (MIT — adapted, attributed in-file) and `pulkit017/job-apply-mcp` (unlicensed — factual selectors only, all code original). These adapters record `apply_audit.status = 'stopped_for_review'` (never `success`) and do NOT go into `my_applications` — nothing was submitted, so the job stays in the match list until the user confirms it in `/tracker`. Shared types live in `platform.ts`. Wherever the codebase says **"Playwright Chromium"** for the user-visible apply browser, read **"real Chrome, launched as a separate browser process/window"**: `src/lib/apply/launcher.ts` (`launchApplyBrowser`) uses `chromium.launchPersistentContext` with `channel: 'chrome'` — the installed Google Chrome running under its OWN process and profile directory (`data/playwright/browser-profile`), which never attaches to the user's everyday browsing windows/tabs. It falls back to Playwright's bundled Chromium binary if the `chrome` channel is unavailable. All three apply adapters (`browser.ts`, `linkedin.ts`, `naukri.ts`) launch through this one helper. Everything else falls back to `browser.ts` — a **visible (non-headless), persistent-context** Playwright window that autofills standard fields and hands off to the user to click Submit (zero-ToS-risk by design; cookies persist under `data/playwright/browser-profile`). Screening answers are hashed and reused via `screening_answers` (`questions.ts`); every attempt is logged to `apply_audit`; per-portal toggles live in the single-row `apply_settings` JSON blob. **Pre-submit validity gate** (`prepare.ts`): before building a plan it checks `expired_at`/`url_status` and does a live `checkJobUrl`, refusing to apply to a closed/dead posting. **Browser success is now three-state**: detected thank-you → `success`; fields filled but no thank-you detected → `submitted_unconfirmed` (not a hard error — detection is heuristic); nothing filled → `error`. `SUCCESS_URL/TEXT_PATTERNS` in `browser.ts` were broadened. **Lever is still `manual`** — no submitter module was ever written for it. **LinkedIn and Naukri used to resolve to `manual` too** (claimed "no submitter module"; the router's `NO_ASSIST_RE` even listed them) until `linkedin.ts`/`naukri.ts` shipped as stop-before-submit adapters and gained their own branch in `identifySubmissionStrategy` (both were removed from `NO_ASSIST_RE`). The `identifySubmissionStrategy` result also drives the BUTTON — `submitsDirectly()` / `strategyActionLabel()` mean a posting is never offered an action its portal can't perform; `submitsDirectly` is still true only for the two disabled API strategies (`greenhouse`/`ashby`). **The 8-minute submission watch no longer runs inside the request handler**: `browserAutofill({ detachWait: true })` returns once the form is filled and `onSettled` records the real outcome later. Screening answers now have a UI (`/settings` → Screening answers, `/api/apply/screening-answers`), and `/api/apply/config` is finally wired up (it previously had zero callers). Required-but-unanswered questions block submission instead of being silently dropped from the multipart body.

**Sync performance — where the time actually goes** (`scripts/ingest-all.ts`, `scripts/ingest-companies.ts`, `src/lib/discovery/*`): the one successful full sync took **3h30m**, and profiling showed SQLite accounted for **0.1-1.4%** of it (a 768-dim cosine scan over 10,721 rows is 84ms). The cost was serialisation, per-seed browser launches and blanket sleeps — not the database. Fixes, all measured:
- **`ingest:all` is now a concurrency pool** (`scripts/ingest-all.ts`, default 4) instead of 11 chained `&&` calls, so wall clock is the SLOWEST source rather than the sum. A failing source no longer aborts the rest (the `&&` chain meant one blocked scraper killed everything after it). Intra-source politeness sleeps are deliberately KEPT — they're per-host courtesy and cutting them risks bans.
- **Concurrent writers need `busy_timeout`.** WAL allows one writer; without it a second writer fails instantly with SQLITE_BUSY. Every ingest script now sets `journal_mode=WAL`, `synchronous=NORMAL` **and** `busy_timeout=15000`. Note `synchronous` is per-CONNECTION, so `db.ts`'s NORMAL never applied to standalone scripts — they were all running at FULL, one fsync per row.
- **`discover`: 27-107 min → 82s cold, 35s warm.** Three changes: the 5 ATS probes per slug run in parallel (they were sequential with a 12s timeout each), seeds process 4-at-a-time (`DISCOVER_CONCURRENCY`) instead of one with a blanket 3s gap, and **one shared Chromium** is passed into `crawlCareersPage` instead of launching one per seed (`opts.browser`; it only closes a browser it launched). Plus a `discovery_probes` table caching ATS detection for `DISCOVERY_PROBE_TTL_DAYS` (14) — board CONTENT is still pulled every run, only detection is cached.
- **LinkedIn skips details it already has.** Its detail URL is deterministic (`/jobs/view/<id>/`), so a row's presence is checked from the id before spending a 6s fetch — it was re-fetching every job every run. Removes 10-25 min.

**Job detail view — tabbed, description first** (`src/components/job-detail-panel.tsx`): the JD used to be section **12 of 12**, behind three cards that render "nothing here yet" placeholders and a ~90-line tracking form, and clamped to 18rem — reading it took a long scroll AND a click. Now four tabs (`DETAIL_TABS`): **Description** (default) · AI review · Company · Apply & track, using the segmented-control idiom already in the repo (`src/app/import/page.tsx:177-197`) rather than adding `@radix-ui/react-tabs` — this project carries only dialog/slot/tooltip. A sticky bar inside the pane's own scroll container keeps the job identity and tabs visible. The header also shows the fit score + the same `reasons` chips as the list row.
- **`jdExpanded` and the LLM format call are now SEPARATE flags.** They used to be one, so expanding the description triggered `/api/jobs/[id]/format`. With the JD expanded by default that would fire an LLM call on every job open — the exact "on-load LLM storm" the cacheOnly work removed. Formatting is now an explicit **"Tidy up"** button (`jdFormatRequested`).
- `/api/matches/[jobId]` reads the **default** pool first (same options as `/api/matches`), falling back to the all-inclusive pool only for hidden/expired/applied jobs. `retrieval` is normalised per-pool, so reading a differently-filtered pool made the detail header show 78 for a job the list showed as 84. It also now passes the **whole** ranked match through — it used to hand-pick four fields, silently dropping `score`, `reasons` and `skillFit`.

**posted_at is TEXT and sources disagree on format.** RSS feeds (We Work Remotely) emit RFC-2822 — `"Mon, 13 May 2024 03:14:30 +0000"` — while everything else emits ISO-8601. Any TEXT comparison on the column then breaks: prune's posting-age rule compares dates lexicographically (correct and index-friendly for ISO-8601, meaningless for "Mon, 13 May"). `normalizePostedAt` / `normalizeStoredPostedAt` in `scripts/shared/freshness.ts` fix this — WWR normalises at ingest, and prune repairs stored rows before reading the column (idempotent, 213 rows repaired on first run). The prune predicate also GLOB-guards the comparison to ISO-shaped values only, because a wrong comparison there EXPIRES a live job.

**Match-list latency — why a page load must never wait for a recompute** (`src/lib/matches.ts`, `scripts/recompute-matches.ts`, `job_skills` table): adding skill-fit scoring made the cold recompute **21s** (from 1.2s), and because the cache signature includes the embedded-job count, a running `npm run embed` invalidated it every batch — so nearly every page load paid the full recompute. Measured 30-50s page loads. Four fixes, in order of impact:
1. **`job_skills` cache.** Extracting a posting's skills costs ~6ms (a ~175-entry vocabulary scanned over the description) and is CONSTANT per job — descriptions never change after ingest. Cached per job it is a one-off; recomputing it for ~1,600 candidates every time was ~10s of the 21s.
2. **`buildProfileSkillSet` once per run.** `analyzeSkillFit`'s fallback calls `hasSkill(profileBlob, skill)` per required skill per job, and each call linear-scans the vocabulary AND compiles a fresh RegExp. Pass the prebuilt Set from any hot path.
3. **Stale-while-revalidate.** A stale-but-present list is returned immediately and refreshed behind the request. Only two paths still block: `refresh: true` (user pressed refresh) and no cached payload at all. Background refresh is debounced to once per 60s per cache key (`BG_REFRESH_MIN_INTERVAL_MS`).
4. **The refresh runs in a DETACHED PROCESS** (`scripts/recompute-matches.ts`), not `setImmediate`. `computeRanked` is synchronous because better-sqlite3 is, so an in-process "background" recompute blocks the event loop for its whole duration (2.4s idle, ~7s while embed competes) and every request arriving in that window stalls. Same reasoning and mechanism as the detached sync orchestrator in `src/lib/sync.ts`.

`RankOpts.cachedOnly` returns null instead of computing when a pool is cold, and warms it in the background. Used by `/api/matches/[jobId]`'s fallback pool — that pool is only consulted for a hidden/expired/applied job, and computing it synchronously added a consistent **4.5s** to every detail request once the previously-top job had been expired by prune.

Measured after: page routes **0.13-0.36s idle**, 0.2-2.3s while a full embed run competes for all 8 cores, no multi-second spikes.

**Embedding is the slow step and it is NOT parallel.** `nomic-embed-text` on CPU Ollama does a batch of 24 six-thousand-char texts in ~67s, so a 5,000-job backlog is ~4 hours. Ollama serialises requests by default (`OLLAMA_NUM_PARALLEL` unset), so a concurrent probe just queues — a "33s single embedding" measurement is queue wait, not compute. Run it at BelowNormal priority if using the app at the same time; `embed-jobs.ts` orders active-first then newest-first so a partial run has embedded the jobs most worth matching.

**Persistence** (`src/lib/db.ts`): one SQLite file at `data/hiresignal.db`, WAL mode, `sqlite-vec` loaded as an extension. All tables are auto-created at module import: `job_postings`, `my_profile`, `my_applications`, `job_evaluations`, `llm_providers`, `company_briefs`, `compensation_data`, `ambitionbox_data`, `layoffs_data`, `screening_answers`, `apply_audit`, `apply_settings`, `resumes` (multi-resume library), `sync_runs` (in-app sync history). There is **no migration system** — the `ADDITIVE_COLUMNS` array at the bottom of `db.ts` applies `ALTER TABLE ADD COLUMN` on load, each guarded by a try/catch that swallows "duplicate column"; add new columns there (or bump schema and tell the user to `npm run db:reset`). For backfilling existing rows' classification, run `npx ts-node scripts/backfill-classifications.ts`.

**Ingestion script duplication is intentional.** Each `scripts/ingest-*.ts` re-declares the schema and `ALL_TERMS`/`isDomainPriority` inline instead of importing `src/lib/*`. This is because ts-node runs them as CJS standalone and importing from `src/lib/db.ts` triggers its auto-schema side effects against a differently-configured DB handle. When editing the ontology or schema, update **both** `src/lib/` and every script that duplicates it.

**Next.js native-module quirks** (`next.config.mjs`): `better-sqlite3`, `sqlite-vec`, and `pdf-parse` are in **`serverExternalPackages`** (top-level — Next 15 RENAMED this from `experimental.serverComponentsExternalPackages`; the old key is silently ignored) and `webpack.externals`. Don't remove these — the app won't build otherwise. `pdf-parse` also requires the workaround `require('pdf-parse/lib/pdf-parse.js')` in `src/app/api/resume/route.ts`; the top-level `require('pdf-parse')` runs a debug test harness that reads a fixture from disk and throws.

## Project conventions

- Path alias: `@/*` → `src/*`.
- API routes live at `src/app/api/**/route.ts` (Next App Router). Client pages are `'use client'` + plain fetch against those routes.
- `my_profile` is a singleton (id = 1); never insert multiple rows.
- When adding a new ingestion source, match the existing pattern: stand-alone script, inline schema + ontology copy, insert via `INSERT OR IGNORE` on `dedup_hash`, leave `embedding` NULL (so `npm run embed` picks it up).
